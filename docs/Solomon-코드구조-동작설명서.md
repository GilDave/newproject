# Solomon · ena-bot 코드 구조와 동작 설명서

## 0. 이 문서를 읽는 법

**목적**: 문제가 생겼을 때 "어느 단계의 어떤 규칙 때문인가"를 정확히 짚기 위한 지도입니다. 순서도(그림 1~8)로 흐름을 먼저 보고, 표와 설명으로 세부 규칙을 확인하세요.

**신뢰 수준 표시**

| 표시 | 뜻 |
|---|---|
| **확인됨** | Solomon 코드를 직접 읽고 테스트로 확인한 내용 (이 문서의 1~12장) |
| **일부 확인** | 사용자가 보여주신 파일·출력에서 확인된 내용 (ena-bot 13장) |
| **확인 필요** | 아직 코드를 보지 못해 추정인 내용. 13장의 명령으로 구조를 뽑아 주시면 채웁니다 |

> 중요: ena-bot 코드는 제 쪽에서 직접 읽을 방법이 없습니다(맥미니 폴더는 클라우드 세션에 열리지 않습니다). 그래서 13장은 일부만 확인된 상태입니다.

## 1. 전체 구성

@@FIG:1@@

- **대시보드 서버**는 화면과 API만 담당합니다. AI를 직접 부르지 않고 **별도 프로세스**(`solomon run` 등)를 실행시킨 뒤, 그 프로세스가 남기는 기록 파일(`events.jsonl`)을 1.5초마다 읽어 화면에 그립니다. 그래서 대시보드를 재시작해도 진행 중인 작업은 계속됩니다.
- **Orchestrator**(`orchestrator.py`)가 한 번의 작업(계획 → 구현 → 검증 → 검수 → 결정)을 지휘합니다. AI 호출은 모두 `providers/`를 거칩니다.
- 모든 기록은 프로젝트 안의 `.solomon/` 폴더에 남고, 한도·이미지 시험 결과·봇 연구실 데이터는 `~/.solomon/`에 있습니다.

## 2. 한 번의 작업 — 준비 단계

@@FIG:2@@

| 단계 | 코드 | 하는 일 | 실패하면 |
|---|---|---|---|
| 계획 | `orchestrator._plan` | 계획 AI에게 목표와 파일 목록(최대 300개)을 주고 **작업 지시서(Order)** JSON을 받습니다. 형식이 틀리면 한 번 더 묻습니다. | 2번 모두 틀리면 `PlanError`로 중단 |
| 계획 검토 | `_plan_review` | 계획 검토 AI(2·3번)가 지시서를 보고 **완료 기준만 추가**합니다. 허용 경로나 한도는 넓힐 수 없습니다. | 검토 실패는 무시하고 진행 |
| 지시서 확정 | `policy.load` | 프로젝트의 **보호 경로**(`.solomon/policy.json`)를 지시서에 합칩니다. 계획 AI가 빼려 해도 빠지지 않습니다. | — |
| 격리 복사본 | `gitops.create_worktree` | 원본과 별개의 작업 폴더를 만듭니다. 커밋 안 된 파일을 포함할지는 설정(`include_uncommitted`)에 따릅니다(비밀 파일 제외). | — |
| 기준선 테스트 | `_build_loop` 앞부분 | **수정하기 전 코드**로 테스트를 한 번 돌립니다. | 원본도 실패하면 `ERROR`로 즉시 중단(AI 호출 없음) |

**작업 지시서(Order)의 내용**: 허용 경로 · 보호 경로 · 완료 기준 · 허용된 삭제 · 최대 파일 수 · 최대 변경 줄 수 · 맥락. 이후 **범위 검사**는 이 지시서만 기준으로 판정합니다(AI의 의견이 아니라 `git diff` 측정값).

## 3. 반복 루프 — 구현에서 통과까지

@@FIG:3@@

한 바퀴가 **시도 1번**입니다. 각 단계의 규칙입니다.

| 단계 | 코드 | 판정 방법 | 통과 조건 |
|---|---|---|---|
| ② 구현 | `_call(builder…)` | 쓰기 가능한 AI(Claude · Codex)가 복사본의 파일을 수정 | AI 호출이 성공 (실패하면 다음 구현 AI로 교대) |
| 변경 수집 | `gitops.collect_changes` | 실제로 파일이 바뀌었는지 | 변경 1개 이상 |
| ③ 범위 검사 | `scope_guard.check` | 허용 경로 안인가, 보호 경로를 건드렸나, 줄 수·파일 수 한도, 삭제 허용 | 위반 0 (**위반이면 변경을 전부 버림**) |
| ④ 테스트 | `verifier.verify` | 프로젝트 테스트 명령의 종료 코드 (제한 600초) | 종료 코드 0 |
| 화면 캡처 | `visual.run_capture` | (설정한 프로젝트만) 캡처 명령 종료 코드 0/3/그 외 | 0 = 계속, 3 = 화면 깨짐(검수 없이 실패), 그 외 = 건너뜀 → 사람 확인 |
| ⑤ 검수 | `_review` | 검수 AI가 diff·테스트 결과를 보고 **blocker가 있으면 FAIL** (minor는 메모만) | 지정한 검수 AI **전원** PASS |
| 이중 실행 | `double_check_tests` | 통과한 테스트를 한 번 더 | 두 번 모두 통과 |
| ⑥ 결정 | `_arbitrate` | 결정권자(Ollama)가 측정값을 보고 채택/반려/사람 확인 | 반려가 아니면 통과 |

**v1.10.1에서 바뀐 것**
- **테스트가 실패한 시도는 검수를 하지 않습니다.** 고치지도 못한 코드를 검수하면 AI 호출만 늘고, 서로 다른 지적이 섞여 구현 AI가 혼란스러워집니다.
- **검수는 "blocker(실제 결함)"만 FAIL**입니다. 이름·스타일·있으면 좋은 테스트 같은 **minor는 메모**로 남고 작업을 되돌리지 않습니다. (이전에는 어떤 지적이든 FAIL이 될 수 있어 검수 AI가 까다로우면 끝없이 되돌아갔습니다.)

### 검수 규칙의 세부

- 검수 AI는 **구현한 AI와 달라야** 합니다(같은 AI가 자기 코드를 검수하지 않음). 구현 AI가 교대하면 그 AI는 검수에서 빠지고 다른 검수 AI가 맡습니다.
- 검수 AI가 판정을 못 내면(시간 초과·형식 오류) 같은 코드에 대해 최대 2번 더 묻습니다. 그래도 안 되면 **구현을 다시 시키지 않고** `ERROR`로 멈춥니다.
- 검수 AI를 같은 AI로 3칸 채우면 비용만 늘고 독립성은 늘지 않습니다(첫 FAIL에서 멈추므로 호출은 1번이지만, PASS 때는 3번 부릅니다).

## 4. 실패 처리: 같은 실패 감지 · 교대 · 초기화

@@FIG:4@@

**서명(signature)**: 실패의 "종류"를 나타내는 짧은 문자열입니다. 예) `tests:tests/test_a.py::test_x`, `review-fail`, `scope:protected path`.
- 같은 테스트가 계속 실패하면 서명이 같아집니다. 검수 AI가 문장을 매번 다르게 써도, 시간·경로·숫자가 바뀌어도 같은 실패로 봅니다.
- **정체 판정**: 최근 6번 안에 같은 서명이 3번 이상이면 정체입니다(다른 종류가 사이에 끼어도 잡힙니다).
- 정체면 코드를 **처음 상태로 되돌리고** "완전히 다른 접근을 하라"고 지시합니다(재시작). 재시작이 2번을 넘으면 **중단**하고, 반복된 실패 이름을 요약에 적습니다.

**이번 "시도 37번" 실패의 구조적 원인 (확인됨)**

| 원인 | 설명 | 조치 (v1.10.1) |
|---|---|---|
| 서명이 너무 예민 | 이전 서명은 실패 메시지 앞 400자를 그대로 비교했습니다. 검수 AI의 문장이나 테스트 출력의 자잘한 차이만으로도 "다른 실패"가 되어 정체 감지가 거의 작동하지 않았습니다. | 실패한 테스트 이름·규칙 종류만 서명에 사용 |
| 밤샘 수정의 시도 횟수 무제한 | 자동 수정은 항목마다 `max_attempts=0`(무제한)으로 실행해서 45분 시간 예산이 유일한 제한이었습니다. | 항목당 최대 12번 |
| 묶음이 너무 큼 | 같은 파일 문제를 최대 6개까지 한 번에 고치게 해서, 변경이 한도(400줄)를 넘기거나 요구가 서로 부딪쳤습니다. | 묶음 최대 3개, 묶음이 실패하면 **문제를 하나씩 쪼개 다시 시도** |
| 검수가 실패한 코드까지 검수 | 테스트가 실패한 시도에도 매번 검수를 불러 상충하는 지적이 쌓였습니다. | 테스트 실패 시 검수 생략 |
| 검수가 모든 지적에 FAIL | 사소한 지적도 FAIL이라 만족시키기 어려웠습니다. | blocker만 FAIL |

**아직 모르는 것**: "왜 테스트가 계속 실패했는가"(고친 코드의 문제인지, 새로 만든 테스트의 문제인지, ena-bot 테스트의 환경 문제인지)입니다. 이 문서의 **14장**이 이를 가려내는 방법입니다.

**교대 규칙**: 구현 AI는 `builder / builder2 / builder3` 순서로 맡습니다. 연속 실패 2번마다, 구현 호출이 실패했을 때, 정체 재시작 때 다음 쓰기 가능 AI로 넘깁니다. 읽기 전용 AI(Antigravity 등)는 조언만 하고 코드를 쓰지 못합니다. **구현 AI 3칸이 모두 같은 AI면 교대해도 달라지는 것이 없습니다.**

**예산(어디서 멈추나)**

| 예산 | 기본값 | 위치 |
|---|---|---|
| 시도 횟수 | 직접 실행 3번 · "끈질기게" 24번 · 밤샘 수정 항목당 12번 | `max_attempts` |
| 시간 | "끈질기게" 180분 · 밤샘 수정 항목당 45분, 전체 360분 | `max_run_minutes`, `autofix` |
| 토큰 | 무제한(설정 가능) | `max_tokens` |
| 같은 실패 | 3번씩, 재시작 2회 | `stagnation_limit`, `max_restarts` |

## 5. 역할 배정과 독립성 규칙

| 단계 | 칸 | 규칙 |
|---|---|---|
| 계획 | planner, planner2, planner3 | 담당이 지시서를 쓰고 2·3번은 검토만(완료 기준 추가) |
| 구현 | builder, builder2, builder3 | 쓰기 가능한 AI는 교대, 읽기 전용 AI는 조언 |
| 검수 | reviewer, reviewer2, reviewer3 | **구현 AI와 달라야** 함, 지정한 AI 전원이 PASS해야 통과 |
| 결정 | arbiter (1칸) | 구현 AI와 달라야 함. 대신할 AI는 없음(막히면 사람 확인) |

- 결정권자(Ollama)는 **모든 관문을 통과한 결과만** 봅니다. 더 엄격하게만 판정할 수 있어서(반려·사람 확인) 실패한 것을 통과시킬 수 없습니다. 확신이 0.6 미만, 고위험 경로(주문·리스크·키·설정 등) 변경, 반려 2번 이상이면 사람 확인으로 돌립니다.
- **그림자 모드**: 결정권자가 모든 시도를 판정하지만 따르지 않고 기록만 합니다. 정답(테스트 결과·사람의 적용/폐기)과 비교해 성적표를 만듭니다.

## 7. 밤샘 자동 수정

@@FIG:6@@

- 분석 결과에서 근거가 확인된 문제를 골라 **파일별 묶음(최대 3개)** 으로 만들고, 항목마다 `run()` 한 번을 실행합니다.
- 통과한 항목은 전용 브랜치(`solomon/autofix-…`)에 커밋되고 **다음 항목은 그 위에서** 시작합니다. 원본 폴더는 바뀌지 않습니다.
- 한 항목의 한도: **12번 · 45분 · 파일 8개 · 변경 400줄**.
- **연속 3건 실패하면 남은 항목은 건너뜁니다**("같은 문제일 가능성이 큼"). 묶음이 실패하면 먼저 문제를 하나씩 쪼개 다시 시도하고, 그래도 실패하는 것만 실패로 셉니다(v1.10.1).
- 결과는 `report.md`, `combined.patch`로 남고 **사람이 적용**합니다.

## 8. 분석 · 영상 분석

| 기능 | 흐름 | 주의 |

## 9. 화면 캡처 관문 · 이미지 시험

- `vision.py`: AI에게 무작위 색 줄무늬 그림을 보여주고 색을 맞히게 해서 **이미지를 볼 수 있는 AI만** 기록합니다(`~/.solomon/vision.json`).
- 관문을 켠 프로젝트는 테스트 통과 뒤 캡처 명령(`policy.json`의 `visual`)을 실행하고, 찍은 그림을 통과한 AI에게만 보여 검수시킵니다. 볼 수 있는 AI가 없으면 결과가 **사람 확인 필요**로 표시됩니다.

## 14. 문제를 정확히 짚는 방법 — 실패한 작업 읽기

**① 대시보드에서 (터미널 없이)**: 작업실 → "시도별 결과"에서 시도마다 확인합니다.

| 보이는 것 | 뜻 | 다음 행동 |
|---|---|---|
| 범위 위반 | 지시서 밖의 파일·보호 경로를 건드렸거나 줄 수 한도 초과 | 목표를 더 좁히거나 보호 경로 확인 |
| 테스트: 실패 + 출력 | 실제로 테스트가 실패 | **출력의 실패한 테스트 이름**을 확인 (아래 ②) |
| 검수: 생략(테스트 실패) | 테스트가 먼저 실패해 검수를 부르지 않음 | 테스트부터 해결 |
| 검수: FAIL + blocker | 검수 AI가 실제 결함을 지적 | 지적 내용이 맞는지 확인 |
| 같은 실패 반복 중단 | 정체 감지 | 요약 끝의 "반복된 실패" 이름이 핵심 단서 |

**② 가장 중요한 단서 = 실패한 테스트 이름과 메시지.** 같은 테스트가 매번 실패하면 구현 AI가 그 요구를 이해하지 못하거나 테스트 자체가 이 환경에서 성립하지 않는 것입니다.

| 증상 | 의심 | 확인 방법 |
|---|---|---|
| 테스트 실패 이름이 매번 같고, 변경 파일은 매번 다름 | 테스트가 환경 문제(데이터 파일·네트워크·시간 의존) | 원본에서 같은 테스트를 직접 실행 |
| 실패하는 테스트가 **AI가 새로 만든 테스트** | AI가 만든 테스트가 잘못됨 | 지시서에 "새 테스트는 기존 방식으로" 추가 |
| 실패 이름이 시도마다 바뀜 | 구현이 점점 불안정 | 목표를 더 작게 쪼개기 |
| 검수 FAIL만 반복, 테스트는 통과 | 검수 기준과 구현의 괴리 | 지적문이 blocker인지 확인(v1.10.1은 minor를 걸러냄) |
| 범위 위반 반복 | 목표가 보호 경로나 한도를 건드림 | 보호 경로 목록·묶음 크기 확인 |

**③ 터미널을 써야 할 때** (붙여넣기용): 해당 항목의 기록 폴더(관리 탭 5W1H "어디서")에서
