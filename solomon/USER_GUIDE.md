# Solomon 사용 가이드 (v1.5)

> 이 문서대로 따라 하면 설치부터 신규 프로젝트, 코드 분석·개선, 밤샘 자동 수정, 되돌리기까지 모두 시험해 볼 수 있습니다.
> 각 단계에는 **기대 결과**가 적혀 있습니다. 다르게 나오면 11장의 "보고 양식"대로 알려주세요.

## 0. Solomon이 하는 일 (한 장 요약)

Solomon은 **여러 AI(Claude, Codex, 선택으로 Antigravity)가 서로의 작업을 검증하며** 코드를 만들고 고치는 도구입니다. 한 AI가 쓰고 다른 AI가 검수하므로 "AI가 자기 코드를 자기가 칭찬하는" 일을 막습니다.

- **비용 안전**: 구독 계정으로 로그인한 CLI만 사용합니다. API 키(종량제)는 쓰지 않으며, 셸에 있어도 호출 전에 제거합니다. 구독 한도가 차면 멈추고 결제로 넘어가지 않습니다.
- **원본 보호**: AI는 항상 격리된 복사본에서 작업합니다. 원본은 **사람이 "적용"을 누를 때만** 바뀝니다.
- **사람은 마지막에 결정**: 대시보드에서 진행 과정과 점검 결과를 보고 적용·커밋·되돌리기를 합니다. 터미널은 시작·종료할 때만 씁니다.

| 하고 싶은 일 | 쓰는 모드 (대시보드 "명령" 카드 맨 위) |
|---|---|
| 아무것도 없는 상태에서 새 프로젝트 시작 | **신규 프로젝트** |
| 이미 있는 프로젝트의 문제를 찾아보기 (코드는 안 바꿈) | **분석 · 읽기 전용** |
| 이미 있는 프로젝트를 고치기·개선하기 | **개선 · 코드 수정** |
| 분석에서 나온 문제를 자는 동안 차례로 고치기 | **밤샘 자동 수정** (분석 보고서의 파란 패널 또는 가운데 열의 카드) |
| 유튜브 영상을 분석해서 내 프로젝트에 쓸 아이디어 얻기 | **영상 분석** |

## 1. 준비

### 1-1. 필요한 것

| 항목 | 설명 | 필수 |
|---|---|---|
| Mac (또는 Linux) | 이 가이드는 Mac 기준입니다 | 필수 |
| Python 3.11 이상 | 맥: `brew install python@3.12` | 필수 |
| git | 맥: `xcode-select --install` | 필수 |
| Claude Code CLI | 구독 계정으로 로그인 | 필수 (기본 계획·검수 담당) |
| Codex CLI | 구독 계정으로 로그인 | 필수 (기본 구현 담당) |
| Antigravity CLI (`agy`) | 구독 계정으로 로그인 | 선택 (3번째 AI: 분석·2차 검수) |
| Ollama (로컬 AI) | 이 컴퓨터에서 도는 모델 (예: `qwen3:8b`). **무료·밖으로 나가지 않음** | 선택 (4번째 AI: 읽기 전용 보조) |

### 1-2. 설치

Solomon 폴더에서 한 번만 실행합니다.

```
bash install.sh
```

이 스크립트는 Python 3.11+ 를 찾고, `.venv` 가상환경을 만들고, Solomon을 설치한 뒤 **자체 점검(selftest)**과 **환경 점검(doctor)**까지 자동으로 돌립니다. 이미 있는 이전 가상환경은 지우지 않고 옆으로 옮깁니다. 코드를 새로 받은 뒤(`git pull`)에도 다시 실행하면 됩니다.

> 설치 중 인터넷이 필요하지만 pip 도구를 받을 뿐이며, AI 서비스에는 접속하지 않습니다.

**기대 결과**: 마지막에 `결과: 12/12 통과` 와 `설치 완료.` 가 보입니다.

### 1-3. AI CLI 로그인 확인 (직접 한 번)

Solomon은 로그인 여부를 대신 확인하지 못합니다. 각 CLI를 직접 실행해서 로그인돼 있는지 보세요.

```
claude --version
codex --version
agy --version
```

각각 터미널에서 한 번 실행해 로그인 화면이 나오면 구독 계정으로 로그인합니다. 로그인한 뒤 AI에게 짧은 질문이 응답되면 준비된 것입니다.

> **절대 하지 말 것**: API 키를 만들어 환경변수에 넣지 마세요. 넣어도 Solomon이 지우지만, 다른 곳에서 종량제 요금이 발생할 수 있습니다.

### 1-4. 환경 점검

```
.venv/bin/solomon doctor
```

**기대 결과**: `[ok]` 가 python, git, claude, codex 에 붙고, 마지막에 `결과: 문제 없음` 이 나옵니다. antigravity 는 `[optional]` 이어도 괜찮습니다. `[missing]` 이나 `[error]` 가 있으면 11장 문제 해결표를 보세요.

git 사용자 정보가 없다는 `[warn]` 이 나오면 한 번만 설정하세요. 대시보드에서 커밋할 때 필요합니다.

```
git config --global user.name "내 이름"
git config --global user.email "내@이메일"
```

터미널 대신 대시보드에서도 됩니다: **프로젝트 탭 맨 아래 `도구 · 설정`** 의 `git 사용자 정보`에 이름·이메일을 넣고 `저장`.

## 2. 시작과 종료

```
bash scripts/start.sh
```

- 터미널을 점유하지 않고 **백그라운드**로 대시보드를 켜고 브라우저를 엽니다. 터미널은 계속 쓰거나 닫아도 됩니다.
- 주소(`http://127.0.0.1:포트/?t=...`)는 이 컴퓨터에서만 열립니다. `t=` 값은 접속 키이니 공유하지 마세요.
- 이미 켜져 있으면 새로 켜지 않고 브라우저만 다시 엽니다.
- Finder에서 `Start-Solomon.command` 를 더블클릭해도 같습니다.

```
bash scripts/stop.sh
```

- Finder에서 `Stop-Solomon.command` 를 더블클릭해도 같습니다.
- 대시보드만 끕니다. **진행 중인 작업은 계속 돌아갑니다** (밤샘 자동 수정 중에 끄셔도 됩니다). 작업까지 멈추려면 `bash scripts/stop.sh --with-runs`.
- 코드를 새로 받은 뒤에는 `bash install.sh` → `bash scripts/stop.sh` → `bash scripts/start.sh` 순서입니다. **첫 설치 이후에는 터미널 없이** 대시보드에서 할 수 있습니다: **프로젝트 탭 → 도구 · 설정 → `Solomon 업데이트 (git pull)` → `대시보드 재시작`** (같은 주소로 자동 재연결되고 화면이 새로 고쳐집니다. 작업이 진행 중이면 재시작은 막힙니다).

한 번에 한 작업만 실행됩니다. 작업 중에 다른 작업을 시작하면 "이미 실행 중인 작업이 있습니다"라고 거절됩니다.

## 3. 화면 지도

### 3-1. 상단

| 요소 | 설명 |
|---|---|
| **대시보드 / 작업실 / 관리 / 프로젝트** | 4개 탭 |
| **현재 작업 표시줄** (탭 오른쪽 알약 모양) | 지금 무슨 작업이 어느 단계인지, 경과 시간, "결정 필요 N건". 누르면 해당 화면으로 이동 |
| 사용 가이드 | 이 문서를 새 탭에서 엽니다 |
| 연결됨 · v1.10.0 | 대시보드 서버 연결 상태 |

### 3-2. 탭별 역할

| 탭 | 용도 |
|---|---|
| **대시보드** | 명령을 내리고(왼쪽), 3개 AI가 일하는 모습(가운데), 토큰·결과(오른쪽)를 봅니다 |
| **작업실** | 진행 중인 작업을 단계 카드와 AI별 상태로 자세히 관찰합니다 (1.5초마다 갱신) |
| **관리** | 결과를 확인하고 **적용·테스트·커밋·되돌리기·폐기·복원**을 합니다. 항목별 5W1H와 적용 판단이 여기 있습니다 |
| **프로젝트** | 프로젝트 **생성·편집·삭제**, 기존 폴더 추가(폴더 찾아보기), 터미널 없이 쓰는 도구(환경 점검·업데이트·재시작). 모든 프로젝트를 **카드**로 한눈에: 개발 진행(분석 → 개선 → 밤샘 수정 → 결정 대기 → 커밋), 성능(통과율·평균 시도·시간·토큰), 사용한 AI·모델. 단계별 AI 참여 도식, AI별 성능, 신규·삭제(휴지통)·복원 |

### 3-3. 대시보드 탭의 명령 카드

위에서 아래로 다음 순서입니다.

1. 모드 버튼: `개선 · 코드 수정` / `분석 · 읽기 전용` / `신규 프로젝트` / `영상 분석`
2. 목표(또는 분석 요청) 입력칸
3. 프로젝트 폴더 입력칸 (신규 프로젝트 모드에서는 이름·종류 입력칸으로 바뀝니다)
4. 역할 배정: 맨 위 **`👑 결정권자`** 한 칸과, 그 아래 **단계(계획·구현·검수) × AI 1·2·3** 칸. AI 1이 담당이고 2·3은 선택 (`없음` 가능)
5. `끈질기게 시도` 체크박스 (기본 켜짐)
6. `프로젝트 설정: 테스트 명령` (접힌 상태, 눌러서 펼침) + `저장`
7. `▶ 실행` / `■ 중지`

**단계마다 AI를 최대 3개까지** 둘 수 있습니다. 칸마다 하는 일이 다릅니다.

| 단계 | AI 1 (담당) | AI 2·3을 지정하면 |
|---|---|---|
| 계획 | 작업 지시서(ORDER)를 씁니다 | **계획 검토**: 지시서를 읽고 우려를 말하고 **완료 기준만 추가**합니다. 수정 가능 범위·한도는 넓힐 수 없습니다 |
| 구현 | 코드를 씁니다 | 쓰기 가능한 AI(Claude, Codex)는 실패가 이어질 때 **교대**(연속 실패 2번마다, 범위 위반·CLI 오류·같은 실패 반복 때는 즉시), 읽기 전용 AI(Antigravity)는 구현 전에 **조언**만 합니다 |
| 검수 | 코드를 검수합니다 | **추가 검수**: 지정한 AI가 **모두 PASS**해야 통과합니다 (앞 AI가 불합격이면 뒤 AI는 부르지 않아 시간을 아낍니다) |
| 범위 검사 · 테스트 | — | AI가 아니라 **기계**가 판정합니다 (AI의 말이 아니라 실제 diff와 테스트 결과) |
| **결정 (결정권자)** | 한 칸 (선택) | **3개 AI 위에서** 최종 채택을 정합니다: 위 모든 게이트를 통과한 결과의 **측정된 증거**를 보고 `채택` / `반려`(구현자에게 이유와 함께 되돌림) / `사람 확인` 중 하나. 실패한 테스트·범위 위반·검수 불합격을 **통과시킬 수는 없고**, 더 엄격하게만 판정합니다 |
| 적용 | — | **사람**이 결정합니다 |

규칙:

- **구현과 검수는 반드시 다른 AI**입니다 (1·2·3차 검수 모두). 같으면 시작이 거절됩니다.
- 구현을 교대하는 AI가 검수 AI이기도 하면, 그 AI가 구현한 시도에서는 자기 코드를 검수하지 않고 다른 검수 AI가 봅니다. 그런 다른 검수 AI가 없는 조합은 거절됩니다.
- Antigravity는 구현 담당(AI 1)이 될 수 없습니다 (읽기 전용). 계획·검수·계획 검토·구현 조언·분석은 가능합니다.
- 계획 검토나 구현 조언 AI가 실패하거나 한도에 걸려도 **작업은 계속**됩니다 (보조 역할이기 때문). 검수 AI가 판정을 못 내면 통과로 처리하지 않고 멈춥니다.

`끈질기게 시도`가 켜져 있으면 통과할 때까지 반복합니다 (최대 180분). 같은 실패가 3번 반복되면 코드를 처음 상태로 되돌리고 다른 방식으로 시도합니다. 끄면 3번 시도 후 멈춥니다.

### 3-4. 탭 사이 이동 (연결 지도)

모든 화면은 서로 연결되어 있어서 터미널이나 복사·붙여넣기 없이 이동합니다.

| 어디서 | 무엇을 누르면 | 어디로 |
|---|---|---|
| 프로젝트 카드 | 맨 아래 큰 버튼 (`▶ 결정 대기 3건 …` 등 **다음 할 일**) | 그 일을 하는 화면 (분석 / 개선 / 밤샘 수정 / 결과함 / 작업실) |
| 프로젝트 카드 | 카드 속 흐름 칸 (분석·개선·밤샘 수정·결정 대기·커밋) | 해당 화면 (그 프로젝트가 자동 선택됨) |
| 프로젝트 카드 | `분석` `개선` `결과함` `작업실` 버튼, 프로젝트 이름 | 대시보드(해당 모드) / 관리 / 작업실 |
| 프로젝트 카드 | AI 칩(`Claude · 10회 · 3.9k`) | 위쪽 AI 성능 카드로 이동·강조 |
| 프로젝트 탭 위쪽 | 결정 대기 숫자 칸 | 관리 탭 (결정이 필요한 프로젝트) |
| 프로젝트 탭 | 단계별 AI 참여 도식의 AI 칩 | 대시보드의 해당 역할 선택칸 |
| 프로젝트 탭 | `+ 신규 프로젝트` | 대시보드 신규 프로젝트 모드 |
| 대시보드 가운데 | AI 원(Claude·Codex·Antigravity) 클릭 | 프로젝트 탭의 그 AI 성능 카드 |
| 대시보드 (영상 분석 화면) | 보고서의 `이 아이디어로 개선 시작` | 개선 모드의 목표 칸에 아이디어가 채워짐 |

| 대시보드 (분석 화면) | 분석 보고서의 `한 번에 순서대로 자동 수정` | 밤샘 자동 수정 작업 시작 → 진행은 아래 `밤샘 자동 수정` 카드와 상단 표시줄 |
| 대시보드 | `결과` 카드의 `5W1H 자세히 · 적용 · 커밋 (관리 탭)` | 관리 탭의 그 실행 |

| 작업실 | 맨 위 `이 실행의 5W1H · 적용 (관리 탭)` `프로젝트 카드` `대시보드로` | 각 화면 |
| 관리 | 위쪽 프로젝트 선택 상자 | 다른 프로젝트의 결과함 |
| 관리 (항목을 연 뒤) | `작업실에서 보기` `대시보드에서 보고서 보기` `프로젝트 카드` | 각 화면 |
| 상단 | 작업 표시줄 / `결정 필요 N건` / `SOLOMON` 로고 | 작업실·대시보드 / 관리 / 대시보드 |

주소 끝에 `#work` `#mg` `#pj` 를 붙이면 그 탭으로 바로 열립니다 (북마크용).

### 3-5. 터미널 없이 하는 일 (프로젝트 탭)

| 하고 싶은 일 | 어디서 |
|---|---|
| 새 프로젝트 만들기 | `+ 신규 프로젝트` (또는 명령 카드 `신규 프로젝트`) |
| 이미 있는 폴더를 프로젝트로 추가 | `+ 기존 폴더 추가` 또는 대시보드 프로젝트 폴더 칸 옆 `찾아보기` — 폴더 목록에서 클릭해서 고릅니다 (경로를 타이핑하지 않아도 됨. 홈 폴더 안만 보임) |
| 빈 새 폴더를 만들어서 고르기 | 위의 `찾아보기` 창 안의 `새 폴더 이름` 칸에 이름을 쓰고 `＋ 새 폴더 만들기` → 만든 폴더 안으로 들어가므로 `이 폴더 선택` (홈 폴더 안에서만) |

| 폴더가 git이 아님 | 카드 `편집` → `git 초기화 + 첫 커밋 만들기` (파일 수와 제외 대상을 먼저 보여주고 확인을 받음. `.env`·키 파일·`.venv`·`node_modules`는 커밋하지 않음) |
| Finder에서 프로젝트·기록 폴더 열기 | 카드 `편집` → 폴더 열기 |
| 삭제 | 카드 `폴더 삭제 (휴지통)` (Solomon이 만든 프로젝트만, 이름 입력 필요, 휴지통에서 복원 가능). 다른 프로젝트는 `목록에서 제거`(파일은 그대로) |
| 환경 점검 / 자체 점검 | `도구 · 설정` → `환경 점검`, `자체 점검 (가짜 AI)` — 결과가 그 아래에 표시됨 |
| yt-dlp 설치 | `도구 · 설정` → `yt-dlp 설치·업데이트` (brew 불필요) |
| git 사용자 정보 | `도구 · 설정` → 이름·이메일 → `저장` |
| 업데이트와 재시작 | `도구 · 설정` → `Solomon 업데이트 (git pull)` → `대시보드 재시작` |

처음 한 번(설치와 시작)만 터미널이 필요합니다.

**가운데 무대의 움직임**: 단계가 넘어갈 때마다 빛 알갱이가 한 AI에서 다음 AI로 날아가며 무엇을 넘기는지(작업 요청 · 작업 지시서 · 변경 diff · 검수 결과) 이름표를 달고 있습니다. 일하는 AI는 궤도 점이 돌고, 아래 **게이트 트랙**(범위 검사 → 테스트 → 검수 → 결정)에 측정 결과가 ✓/✗로 켜집니다. 실패하면 붉은 파문과 함께 "재시도"가 구현 AI로 되돌아가고, 통과하면 결정권자 쪽에서 초록 불꽃이 터집니다. 작업이 없을 때는 **▶ 흐름 미리보기**를 누르면 AI 호출 없이 이 연출을 볼 수 있습니다.

### T6. 밤샘 자동 수정 (AI 사용 — 처음엔 1~3건만)

분석 결과(T4)를 **한 번의 클릭으로 순서대로** 알아서 고칩니다. 문제마다 직접 목표를 만들어 실행할 필요가 없습니다. 각 수정은 T5와 같은 검증을 거치고 **앞 수정 위에 이어서** 쌓입니다.

**방법 A (권장): 분석 보고서에서 바로**

1. 분석이 끝난 프로젝트의 `분석 · 읽기 전용` 화면에서 보고서 맨 위의 파란 **"한 번에 순서대로 자동 수정"** 패널을 봅니다.
2. 문제마다 있는 체크박스로 대상을 고릅니다. 처음에는 **근거 확인된 문제(중간 이상)** 가 미리 체크돼 있습니다. `전체 선택` · `근거 확인된 것만` · `2개 이상 AI가 지적한 것만` · `선택 해제` 버튼으로 한 번에 바꿀 수 있습니다.
3. `같은 파일은 한 번에 묶어서 (빠름)` 를 켜 둡니다 (기본). 같은 파일의 문제를 **한 번의 작업**(계획 1번, 구현 1번, 검수 1번)으로 고쳐서 문제 수가 많을 때 훨씬 빠릅니다. 파일당 최대 6건씩 묶습니다.
4. 제한 시간을 고르고 `▶ 선택한 N건 전부 순서대로 자동 수정` 을 누릅니다. **처음에는 1~3건만 선택해서** 시험하세요.

**방법 B: 필터로 고르기**

1. T4의 분석이 끝난 프로젝트를 선택하고, **개선 모드에서 테스트 명령이 저장돼 있어야 합니다** (없으면 시작되지 않습니다).
2. 대시보드 탭 가운데의 **밤샘 자동 수정** 카드:
   - 최소 심각도: `보통 이상`
   - 최대 수정 개수: **처음엔 3**
   - 제한 시간: `2시간`
3. `밤샘 자동 수정 시작`.

**기대 결과**:
- 카드 아래에 배치 번호와 항목별 상태(🔄 진행, ✅ 수정됨, ❌ 실패, ⏭ 건너뜀)가 실시간으로 나옵니다.
- 끝나면 **관리 탭**에 `밤샘 수정` 항목이 생기고, 항목별(`problem …`)로 펼쳐집니다. 각 항목에 `변경 보기 / 적용 / 폐기` 가 있습니다.
- 현재 브랜치와 작업 폴더는 **바뀌지 않았어야** 합니다. 수정은 별도 브랜치 `solomon/autofix-<번호>` 에만 있습니다.

아침에 하는 일: 관리 탭에서 배치를 열어 → **적용 판단**과 **5W1H의 "왜"**(어느 분석 지적 때문에 고쳤는지)를 읽고 → 마음에 드는 항목만 `적용` (또는 배치 전체 `적용`) → `테스트 실행` → `커밋`.

`최대 수정 개수`에는 `전부 (제한 없음)` 도 있습니다.

멈추는 조건: 시간 예산, 구독 한도 소진, 3건 연속 실패, 수정 전 테스트 실패, 중지 버튼. 실패한 항목은 건너뛰고 계속합니다. 맥은 작업 중 잠자기를 막습니다. 전원은 연결해 두세요.

### T8. 단계마다 AI 3개 참여 (AI 사용)

세 AI(Claude, Codex, Antigravity)가 모두 로그인돼 있어야 합니다. 작은 목표로 하세요.

1. `개선 · 코드 수정` 모드에서 프로젝트를 고르고 테스트 명령이 저장돼 있는지 확인합니다 (T5-2).
2. 역할 배정 격자를 이렇게 채웁니다.

   | | AI 1 | AI 2 | AI 3 |
   |---|---|---|---|
   | 계획 | Claude | Antigravity | 없음 |
   | 구현 | Codex | Claude | Antigravity |
   | 검수 | Claude | Antigravity | 없음 |

   구현 AI 2의 Claude는 교대 후보이고, AI 3의 Antigravity는 구현 조언을 합니다. Claude가 구현할 차례에는 Claude 대신 Antigravity가 검수합니다.
3. 목표에 작고 구체적인 한 가지를 적고 `▶ 실행`.

**기대 결과** (관리 탭 → 항목 열기 → 단계별 진행 과정):
- 준비: `계획`, `계획 검토 · antigravity` (우려와 **완료 기준 추가** 내용이 줄로 나옴), `작업지시서`
- 시도 1: `구현 자문`(Antigravity) → `구현`(Codex) → 바뀐 파일 → 범위 검사 → 테스트 → `검수 · claude` → `검수 · antigravity` → 테스트 재확인

- 적용 판단의 `작성자와 검수자` 줄: `구현 … ≠ 검수 …`
- 프로젝트 탭의 AI 성능 카드에 각 AI의 역할 칩(`계획 검토1`, `2차 검수`, `구현 보조…`)이 쌓입니다.

시도가 한 번에 통과하면 교대는 일어나지 않습니다 (정상). 교대를 보고 싶으면 일부러 어려운 목표를 주거나 `solomon selftest`의 8번째 점검을 참고하세요 (가짜 AI로 같은 흐름을 재현합니다).

프로젝트가 2개 이상 있을 때 하세요 (T2·T3에서 만든 `guide-test`, `calc-test`, 기존 프로젝트).

**기대 결과**:

3. 정렬 상자를 `주의 필요한 순`(기본: 작업 중·결정 대기가 위로) / `최근 활동 순` / `이름 순`으로 바꿔 봅니다.

### T10. 유튜브 영상 분석 (AI 사용)

**어떻게 분석하나**: 영상을 AI가 "보는" 것이 아니라 **자막(말한 내용)을 읽습니다.** AI마다 영상을 직접 열 수 있는지가 다르고, 못 여는 AI도 그럴듯한 답을 지어내기 때문입니다. 자막은 모든 AI가 읽을 수 있는 글이라서, 선택한 AI(최대 3개)가 **같은 자막을 각자** 분석하고, AI가 인용한 문장이 자막에 **실제로 있는지 기계가 대조**합니다 (코드 분석과 같은 방식). 시각 링크(▶ 0:05)의 시각도 AI의 말이 아니라 자막에서 가져옵니다.

**준비 (권장)**: 자막을 자동으로 가져오는 성공률을 높이려면 한 번만 설치하세요.

Homebrew가 있으면:

```
brew install yt-dlp
```

`brew: command not found` 가 나오면 Homebrew가 없거나 이 터미널이 못 찾는 것입니다. **brew 없이** Solomon 가상환경에 설치하면 됩니다 (Solomon 폴더에서):

```
.venv/bin/python -m pip install yt-dlp
```

Solomon이 같은 가상환경의 yt-dlp를 자동으로 찾습니다 (설치 뒤 대시보드를 재시작하세요: `bash scripts/stop.sh` 후 `bash scripts/start.sh`). 확인은 `.venv/bin/solomon doctor` 의 `yt-dlp` 줄입니다. 둘 다 안 해도 동작은 시도합니다 (유튜브 자막을 직접 가져옴). 그래도 안 되면 자막을 직접 붙여넣을 수 있습니다.

**10-1. 각 AI가 영상을 직접 볼 수 있는지 시험 (선택, 1~3분)**

1. 대시보드에서 `영상 분석` 모드를 누르고, 프로젝트 폴더가 입력돼 있는지 확인합니다 (결과가 그 프로젝트에 저장됩니다).
2. `유튜브 영상 주소`에 짧고 자막이 있는 영상 주소를 넣고, 분석에 참여할 AI를 고른 뒤 `AI별 영상 직접 시청 시험`을 누릅니다.
3. 각 AI에게 "이 영상을 열고 제목을 말하라"고 시키고 **유튜브가 알려주는 진짜 제목과 비교**합니다.

**기대 결과** (명령 카드 아래 AI 칩):

| 표시 | 뜻 |
|---|---|
| `직접 시청 확인됨` | 진짜 제목을 맞힘 → 이 AI는 영상을 실제로 열 수 있음 (`직접 시청도 사용` 체크 가능) |
| `추측 (제목이 틀림)` | "볼 수 있다"고 했지만 제목이 틀림 → **영상을 보지 않고 지어낸 것**. 직접 시청에 쓰지 마세요 |
| `직접 볼 수 없음` | 스스로 못 연다고 답함 (정상. 자막 분석은 가능) |
| `확인 불가` | 진짜 제목을 가져오지 못해 비교할 수 없음 |
| `호출 실패` | CLI 오류 또는 한도 |

터미널에서도 같은 시험을 할 수 있습니다: `solomon video --probe` (주소 필요). 결과는 기억되어 다음에 칩으로 보입니다. 이 시험으로 "유튜브 영상은 어느 AI가 잘 보는가"를 직접 확인하세요. 일반적으로 Google 계열(Antigravity)이 영상을 직접 여는 데 유리하다고 알려져 있지만, **구독 로그인 CLI에서 실제로 되는지는 이 시험 결과가 정답**입니다.

**10-2. 영상 분석 실행**

1. `영상 분석` 모드, 유튜브 주소 입력.
2. 분석 요청에 중점을 적습니다. 비워 두면 요약·핵심·확인할 주장·해볼 것 전체를 봅니다. 예: `손절·리스크 관리 규칙과, 숫자로 검증해야 할 주장 위주로`.
3. 프로젝트에 적용할 아이디어도 받고 싶으면 `위 프로젝트에 적용할 아이디어도 찾기`를 켭니다 (프로젝트의 파일 목록과 README 앞부분이 AI에게 전달됩니다).
4. 분석에 참여할 AI를 고르고 `▶ 영상 분석 시작`.
5. 자막을 못 가져오면 오류가 뜹니다. 영상 아래 `⋯ → 스크립트 표시`에서 복사해 `자막을 직접 붙여넣기`에 넣고 다시 시작하세요. `0:05` 같은 시각이 붙어 있으면 시각 링크가 만들어집니다.

**기대 결과** (가운데 열 `영상 분석 결과` 카드):
- 영상 제목(유튜브로 연결), 채널, 자막 언어·출처, 길이, AI별 칩(`항목 N개 · 근거 확인 M`).
- AI별 요약 (펼침).
- **핵심 / 확인할 주장 / 해볼 것** 목록. 항목마다: 지적한 AI 수(`2/3`), `▶ 0:05` 시각 링크, 인용 문장, `근거 확인됨 ✓` 또는 `근거 불일치 ✗ (AI가 지어냈을 수 있음)`.
- 켰다면 `이 프로젝트에 적용할 아이디어`와 `이 아이디어로 개선 시작` 버튼 → 개선 모드의 목표 칸이 채워집니다.
- 맨 아래 한계 안내와 `5W1H 보기 (관리 탭)`. 보고서는 `<프로젝트>/.solomon/videos/<번호>/report.md` 에도 저장됩니다.

**읽는 법**: `확인할 주장`은 영상이 **한 말**이지 **사실이 아닙니다.** (예: "손절 2%가 가장 좋다") 숫자·수익 주장은 직접 검증하기 전에는 믿지 마세요. 근거 불일치 항목은 무시해도 됩니다. 여러 AI가 같은 시각에서 같은 점을 지적하면 신뢰도가 높습니다.

**한계**: 화면에 보이는 차트·그림은 분석되지 않습니다 (자막이 없는 영상, 음성이 거의 없는 영상은 분석이 어렵습니다). 아주 긴 영상은 앞부분(약 15만 자)까지만 분석하고 그 사실을 알려줍니다. 비공개·연령 제한·지역 제한 영상은 자막을 가져오지 못할 수 있습니다. 재생목록·채널 주소는 지원하지 않습니다 (개별 영상 주소만).

터미널로 하려면:

```
solomon video https://www.youtube.com/watch?v=영상번호 --project /경로 --focus "리스크 규칙" --context
solomon video https://youtu.be/영상번호 --transcript-file 자막.txt
```

**결정권자의 규칙 (모두 코드로 고정)**:

| 상황 | 결과 |
|---|---|
| 테스트 실패 · 범위 위반 · 검수 불합격 | 결정권자는 **묻지도 않고** 통과시킬 수도 없음 |
| `채택`이라고 했지만 확신이 0.6 미만 | **사람 확인**으로 내려감 |
| 주문·리스크·설정·`.env` 같은 **고위험 경로 이름**을 건드림 | 채택했어도 **사람 확인** |
| `반려` | 구현자에게 이유·조건과 함께 되돌려 다시 시도 (같은 작업에서 2번까지, 그 뒤에는 막지 않고 사람 확인) |

**성적표 읽는 법**: `채택한 것을 사람도 적용한 비율`이 핵심입니다. 결정권자가 채택한 결과를 사람이 적용했는지 폐기했는지를 비교합니다. **표본이 30건 이상 쌓이기 전에는 숫자를 믿지 마세요.** 일치율이 높다고 해서 판단이 옳다는 뜻은 아닙니다 (사람이 무심코 다 적용했을 수도 있습니다). 정확도에 대한 의심이 들면 `사람 확인` 비율을 늘리는 쪽(더 엄격하게)으로만 조정하세요.

설정 (`solomon.toml`):

```
[roles]
arbiter = "ollama"

[loop]
arbiter_min_confidence = 0.6
arbiter_max_rejects = 2
```

터미널: `solomon run "목표" --project /경로 --arbiter ollama`.

### T15. 화면 캡처 관문 — AI가 화면을 눈으로 보고 검수 (화면이 있는 프로젝트)

코드와 테스트만으로는 "화면이 예쁜지, 깨졌는지"를 알 수 없습니다. 이 관문은 테스트가 통과한 결과를 **실제로 띄워 스크린샷을 찍고, 이미지를 볼 수 있는 검수 AI가 그 화면을 직접 보고** 판정하게 합니다.

1. **AI별 시험 (한 번만)**: 프로젝트 탭 → 도구 · 설정 → **화면 보기 능력 시험**. 색깔 줄무늬 그림을 보여주고 색을 맞히게 해서 통과한 AI만 이미지 검수에 씁니다. (구독 사용량이 아주 조금 듭니다.) 결과는 "이미지를 볼 수 있는 AI: Claude ✓ · Codex ✗" 식으로 표시됩니다. 지원하지 않는 AI는 화면을 보지 못하니 판정에서 외모를 따지지 않습니다.
2. **프로젝트에 켜기**: 프로젝트 카드 **편집** → **화면 캡처 관문** → (Solomon 자신은) **이 프로젝트에 맞는 명령 채우기** → 저장. 명령은 직접 정할 수도 있습니다. `{out}`에 png를 저장하면 됩니다. 종료 코드 **0** = 정상, **3** = 화면이 깨짐(구현 AI에게 되돌림), 그 밖 = 캡처를 못 함(건너뜀, 사람이 확인).
3. **실행하면**: 구현 → 범위 검사 → 테스트 → **화면 캡처** → 검수(그림을 보는 AI) → 결정 순서입니다. 작업실 "시도별 결과"에 AI가 본 **그 스크린샷이 그대로** 나오고, 눌러서 크게 볼 수 있습니다. 무대의 게이트 트랙에도 "화면 캡처" 칸이 생깁니다.

5. 캡처를 하려면 Node.js와 Playwright가 필요합니다 (가이드 PDF를 만들 때 쓰는 것과 같습니다). 없으면 "건너뜀"으로 표시됩니다.

### T16. 플랜 B — 한 AI의 사용 한도가 끝나도 밤샘은 계속

Claude(또는 다른 AI)가 구독 사용 한도에 걸리면 **같은 단계를 다른 로그인 AI가 즉시 이어받습니다**. 결제형 API로 넘어가지는 않습니다.

- 구현은 쓰기 가능한 AI(Codex ↔ Claude), 계획·검수는 Claude · Codex · Antigravity 중 남은 AI가 맡습니다. 검수 AI는 항상 구현 AI와 달라야 한다는 규칙이 그대로 지켜집니다. 결정권자는 대신 맡는 AI 없이 "사람 확인"으로 갑니다.
- 한도에 걸린 AI는 **재개 시각**까지(CLI가 알려주면 그 시각, 아니면 120분) 피합니다. 이 기록은 모든 작업이 함께 보므로 다음 항목도 시작부터 다른 AI를 씁니다. 한도가 풀리면 원래 배정으로 돌아갑니다.
- **모든 AI가 한도에 걸리면** 끝내지 않고 가장 빠른 재개 시각까지 기다렸다가 이어서 진행합니다.
- 화면: 작업실 실행 카드에 "⚡ Claude 한도 소진 → Codex가 구현을 자동으로 이어받았습니다"가 보이고, 기록의 타임라인에도 남습니다. 프로젝트 탭 → 도구 · 설정에서 "한도에 걸린 AI"를 보고 **한도 기록 지우기**로 수동 초기화할 수 있습니다. (벤치마크는 AI 조합을 재는 도구라 플랜 B를 쓰지 않습니다.)
- 끄거나 순서를 바꾸려면 `solomon.toml`의 `[failover]`를 보세요.

권고는 세 가지입니다: ✅ 권장 / ⚠ 확인 필요 / ⛔ 비권장. **점검표는 파이프라인이 실제로 측정한 사실**이며 AI의 주장이 아닙니다. 그래도 최종 결정은 diff를 직접 읽고 하세요. 테스트가 없는 프로젝트는 "검증 안 됨" 경고가 붙습니다.

### 5-3. 5W1H

관리 탭 아래쪽 "모든 기록"에서 번호(개선 / 밤샘 수정 / 분석)를 누르면 볼 수 있습니다.

| 칸 | 내용 |
|---|---|
| 누가 | AI별 역할·호출 수·시간·토큰, 검수 판정 |
| 무엇을 | 목표, 결과, 바뀐 파일 |
| 언제 | 시작·끝·걸린 시간, 적용·커밋 시각 |
| 어디서 | 프로젝트, 기록 폴더, 패치 파일, (밤샘) 수정 브랜치 |
| 왜 | 요청 내용, (밤샘) 어느 분석 지적 때문인지 |
| 어떻게 | 시도 횟수, 테스트 결과, 진행 기록 |

### 5-4. 프로젝트 탭의 숫자 읽는 법

| 지표 | 계산 | 읽는 법 |
|---|---|---|
| 통과율 | 통과한 개선 ÷ 끝난 개선 (한도·중지 포함) | 낮으면 목표가 크거나 테스트가 불안정할 수 있음 |
| 평균 시도 | 통과한 개선의 평균 시도 횟수 | 1에 가까울수록 한 번에 통과 |
| 평균 시간 | 통과한 개선의 시작~끝 | AI 응답 시간 포함 |
| 토큰 | CLI가 알려준 값 + 알려주지 않은 호출은 글자 수로 추정 | 추정 포함. 구독 한도 차감량과 같지 않을 수 있음 |
| 구현 성공률 (AI별) | 그 AI가 만든 **최종 통과 시도 수** ÷ 그 AI가 구현한 시도 수 | 높을수록 첫 시도에 잘 만드는 AI |
| 검수 불합격 지적 (AI별) | FAIL 판정 ÷ 전체 판정 | **높다고 나쁜 것이 아닙니다.** 엄격하게 잡아낸다는 뜻일 수 있으니 구현 성공률과 함께 보세요 |
| 결정 대기 | 적용 전 또는 적용만 하고 커밋 안 한 결과 수 | 0이 될 때까지 처리하는 것이 목표 |

이 숫자는 모두 로그에서 집계한 값이며 AI의 의견이 아닙니다. 기록이 쌓일수록 어느 AI에게 어느 단계를 맡길지 근거가 생깁니다.

## 6. 주요 개념

- **단계별 AI 참여**: 계획·구현·검수에 각각 최대 3개 AI. 3-3의 표를 보세요. 범위 검사와 테스트는 일부러 AI가 아니라 기계가 판정합니다 (AI가 자기 결과를 채점하는 일을 막기 위해).
- **묶어서 고치기**: 같은 파일의 문제 여러 건을 한 번의 작업으로 고칩니다. 계획·검수 호출이 줄어 속도가 크게 빨라집니다. 한 묶음이 실패하면 그 파일의 문제 전체가 실패로 기록되므로, 문제를 하나씩 확실히 고치고 싶으면 끄세요.
- **ORDER(작업 지시서)**: 계획 AI가 만든 "무엇을 어디까지 고칠지" 계약서. 수정 가능 경로, 보호 경로, 완료 기준, 파일·줄 한도가 들어 있습니다. 구현 AI가 이 범위를 벗어난 수정은 자동으로 버려집니다.
- **범위 검사(Scope Guard)**: AI의 말이 아니라 실제 git diff로 범위 위반을 판정합니다.
- **끈질기게 시도**: 통과할 때까지 반복. 시간(기본 180분)·토큰 예산, 구독 한도에서 멈춥니다. 같은 실패가 반복되면 "완전히 다른 접근"을 시킵니다.
- **시작 전 점검(baseline)**: 수정하기 전 코드의 테스트가 이미 실패하면 AI를 호출하지 않고 멈춥니다 (토큰 절약). 신규 프로젝트의 첫 실행은 건너뜁니다.
- **토큰 표시**: 숫자 앞의 `~` 는 추정치입니다. 구독 한도 차감량과 정확히 같지 않을 수 있습니다.

## 7. 안전 규칙 요약

| 규칙 | 내용 |
|---|---|
| 원본 불변 | 사람이 `적용`을 누르기 전에는 원본 폴더가 바뀌지 않습니다 |
| 커밋은 사람이 | 적용만으로는 커밋되지 않습니다. 밤샘 수정은 별도 브랜치에만 커밋합니다 |
| 결과에 섞이지 않는 파일 | 커밋은 그 항목이 바꾼 파일만 대상으로 합니다 (봇이 갱신하는 파일 등은 건드리지 않음) |
| 삭제 제한 | Solomon이 만든 프로젝트만 삭제 가능, 이름 입력 필요, 휴지통으로 이동 |
| 비밀 보호 | `.env`·`*.pem`·`*.key` 는 AI에게 보내지 않고, 토큰·비밀번호처럼 보이는 값은 가려서 보냅니다 |
| 종량제 차단 | API 키 환경변수를 제거하고 구독 CLI만 호출. 한도 소진 시 멈춤 |
| 접속 제한 | 대시보드는 이 컴퓨터(127.0.0.1)에서만 열리며 접속 키가 필요합니다 |

## 8. 파일이 저장되는 곳

| 위치 | 내용 |
|---|---|
| `<프로젝트>/.solomon/runs/<번호>/` | `events.jsonl`(모든 단계 기록), `result.json`, `result.patch`(통과 시), `last_attempt.patch` |
| `<프로젝트>/.solomon/analyses/<번호>/` | `report.md`, `analysis.json`, `events.jsonl` |
| `<프로젝트>/.solomon/batches/<번호>/` | 밤샘 수정의 `report.md`, `combined.patch`, `batch.json`, `events.jsonl` |
| `<프로젝트>/.solomon/inbox.json` | 적용·커밋·폐기 같은 결정 기록 |
| `<프로젝트>/.solomon/worktrees/` | 작업 중인 격리 복사본 (끝나면 정리됨) |
| `~/.solomon/dashboard.log` | 대시보드 로그 (접속 키가 들어 있어 비공개) |

`.solomon/` 는 git에서 자동으로 제외되므로 커밋에 섞이지 않습니다.

## 9. 설정 (필요할 때만)

기본값으로 모두 동작합니다. 바꾸고 싶을 때만 설정 파일을 만드세요.

```
.venv/bin/solomon init
```

현재 폴더에 `solomon.toml` 이 만들어집니다. 주요 항목:

| 항목 | 설명 |
|---|---|
| `[roles]` | 기본 역할 배정 (계획·구현·검수·2차 검수) |
| `projects_root` | 신규 프로젝트 폴더 위치 (기본 `~/Solomon-Projects`) |
| `[loop] max_attempts` | 0 이면 통과할 때까지 |
| `[loop] include_uncommitted` | `false` 로 하면 커밋된 상태(HEAD)만 사용 |
| `[safety]` | 한 번에 바꿀 수 있는 파일·줄 수 한도, 허용 테스트 명령 목록 |

대시보드를 켤 때 설정 파일을 쓰려면 `bash scripts/start.sh --config /경로/solomon.toml`.

## 10. 명령어 모음 (대시보드로 모두 가능하지만 필요할 때)

```
solomon doctor
solomon selftest
solomon analyze --project /경로 --focus "예외 처리"
solomon run "목표" --project /경로 --persist --max-minutes 120
solomon autofix --project /경로 --max-fixes 3
solomon status --project /경로
solomon runtests --project /경로
```

가상환경 안에 설치되어 있으므로 `.venv/bin/solomon` 으로 실행하거나 `source .venv/bin/activate` 후 `solomon` 만 입력합니다.

## 11. 문제 해결과 보고

### 11-1. 증상별 조치

| 증상 | 원인 | 조치 |
|---|---|---|
| `doctor` 에 `[missing] claude` / `codex` | CLI가 PATH에 없음 | 해당 CLI를 설치하고 새 터미널에서 `claude --version` 이 되는지 확인. 안 되면 `solomon.toml` 의 `[executables]` 에 경로 지정 |

| 같은 문구인데 pytest 오류가 아님 | 프로젝트 테스트 자체가 실패 | 프로젝트 폴더에서 같은 명령을 직접 실행해 원인을 해결 |
| "테스트 명령이 없으면 밤샘 자동 수정을 하지 않습니다" | 테스트 명령 미설정 | 개선 모드에서 `프로젝트 설정: 테스트 명령` 저장 |
| `NO_OUTPUT_TIMEOUT: no output for 180s` (Claude 구현 실패) | v1.5.3 이하: Claude는 작업이 끝날 때까지 출력이 없는데 3분 침묵으로 오판해 중단함 | **v1.5.3 이상으로 업데이트** (Claude는 침묵으로 중단하지 않고 구현 호출은 최대 20분까지 기다림) |
| `NO_OUTPUT_TIMEOUT` / Antigravity가 느림 | agy 응답 지연 | Antigravity를 역할에서 빼도 동작합니다. 한 번 단독으로 `agy` 실행해 로그인 상태 확인 |
| "구독 사용 한도에 도달해 멈췄습니다" | 구독 한도 소진 | 한도가 풀린 뒤 다시 실행. API로 넘어가지 않습니다 |
| 적용 시 "패치를 적용하지 못했습니다" | 작업 폴더가 그사이 바뀜 / 이미 반영됨 | 관리 탭의 "작업 폴더 충돌" 경고를 보고, 겹치는 파일을 커밋하거나 정리한 뒤 다시 시도 |
| 커밋 버튼이 "git 사용자 정보가 없습니다" | git 이름·메일 미설정 | 1-4의 `git config --global …` |
| 대시보드 "연결 끊김" | 대시보드가 꺼짐 | `bash scripts/start.sh` (새 주소가 열립니다) |
| 화면 아래에 "not found" 또는 "대시보드 서버가 옛 버전입니다" 알림 | 코드를 새로 받았는데(`git pull`) 대시보드를 다시 시작하지 않음 | `bash scripts/stop.sh` 후 `bash scripts/start.sh` (진행 중인 작업은 계속됩니다) |
| 브라우저가 안 열림 | 자동 열기 실패 | `cat ~/.solomon/dashboard.url` 의 주소를 브라우저에 붙여넣기 |
| 포트 사용 중 | 8765가 이미 사용됨 | 자동으로 8766… 중 빈 포트를 씁니다. 주소는 위 파일에 있음 |
| `이미 실행 중인 작업이 있습니다` | 한 번에 한 작업만 가능 | 끝나길 기다리거나 `■ 중지` |
| 시작이 "검수 AI 중에 구현 AI가 있습니다"로 거절됨 | 구현과 검수에 같은 AI를 골랐음 | 역할 격자에서 검수 칸(1·2·3)에 구현 AI(Codex 등)가 없게 고르세요 |
| "구현 보조 X가 구현할 차례에는 검수할 다른 AI가 없습니다" | 구현 교대 후보가 유일한 검수 AI이기도 함 | 검수 칸에 다른 AI를 하나 더 지정 |
| 영상 분석이 "자막을 가져오지 못했습니다" | 자막이 없거나 비공개·연령/지역 제한, 또는 유튜브의 자동 수집 제한 | `brew install yt-dlp` 후 다시 시도, 그래도 안 되면 자막을 직접 붙여넣기 |
| 영상 분석 항목이 대부분 `근거 불일치` | AI가 자막에 없는 문장을 인용함 (직접 시청 AI가 보지 않고 지어냄 등) | 직접 시청 사용을 끄고 자막만으로 분석 (10-1의 시험에서 `확인됨`인 AI만 직접 시청에 쓰세요) |
| 프로젝트 탭의 Ollama 카드가 `서버가 꺼져 있거나 모델이 없음` | Ollama 앱이 실행 중이 아님, 또는 설정의 `model` 이름이 설치된 모델과 다름 | Ollama 앱을 실행하고 `ollama list` 의 이름을 `solomon.toml` 의 `[ollama] model` 에 적기 |
| `ollama: 입력이 문맥 길이를 꽉 채워 … 잘렸을 수 있어` 오류 | 입력이 `num_ctx` 보다 길어 Ollama가 앞부분을 잘랐음 | `[ollama] num_ctx` 를 늘리거나 더 짧은 입력으로 사용 |
| 이전에 만든 `.venv` 가 Python 3.9 | 오래된 가상환경 | `bash install.sh` 가 자동으로 옆으로 옮기고 새로 만듭니다 |
| 개선이 "git 저장소가 아니라" 거절됨 | git 미초기화 | 폴더에서 `git init`, 첫 커밋. 분석은 git 없이 가능 |
